# Interview Package Contract

Interview Packages are owner-private source registers for real interview
events. They may be assigned to one exact Loop and optional Round, but they are
not Loops, practice activities, transcripts generated by Interview Arc, or
Interview Material.

Owning issue: [#415](https://github.com/Vinosaamaa/interview-arc/issues/415).

## Authority boundary

- The authenticated website derives owner scope from the verified request. A
  browser payload never supplies an owner ID or private R2 locator.
- Creating a package requires an explicit consent affirmation. Interview Arc
  records the affirmation but cannot determine whether recording was lawful.
- Adding a package never creates or revises a Loop, Role Brief, practice
  activity, or Interview Material.
- A package may link one exact current Interview Material revision without
  changing it.
- The website may prepare an owner-authored material proposal from an explicit
  checked source set. A second confirmation creates one append-only material
  revision through the narrow `website_owner` adapter. It never invokes AI.
- The `loop_recorder` authorization remains exclusive to specialist-driven
  Loop and material commands. Website package confirmation cannot impersonate
  it or broaden its authority.

## Storage and limits

| Source | Allowlist | Per-file limit | Representation |
| --- | --- | ---: | --- |
| Audio | MP3, M4A/MP4, WAV, WebM, Ogg | 1 GiB | Immutable private R2 bytes |
| Supplied transcript | UTF-8 TXT, VTT, SRT | 512 KiB | Immutable private R2 bytes plus deterministic D1 cue projection |
| Document | PDF, UTF-8 TXT, Markdown | 50 MiB | Immutable private R2 bytes; PDF is download-only |
| Image | PNG, JPEG, WebP | 25 MiB | Immutable private R2 bytes |
| External link | Credential-free HTTPS | 2,000 characters | Versioned D1 snapshot; never crawled |
| Owner note | Plain owner-authored text | 20,000 characters | Append-only D1 revisions |

One package permits at most 20 file sources, 50 note/link entries, and 2 GiB
of file bytes. Browser uploads use contiguous 5 MiB multipart parts. D1 owns
the server checkpoint; the owner can reselect the same exact file and resume
from the recorded byte boundary for 24 hours. Completed source bytes are
retained until governed package deletion.

The Worker validates the declared allowlist, exact byte count, file signature,
UTF-8 encoding where applicable, streaming SHA-256, R2 metadata, and exact R2
readback before marking a source ready. HTML, SVG, archives, mislabeled bytes,
and unsupported media types are rejected. Duplicate detection is owner-scoped
and never provides a cross-owner content oracle.

## State and revisions

- Package, assignment, entry, source, material-link, and proposal writes use
  stable operation IDs and optimistic revisions.
- Exact retries replay the saved receipt. Reusing an operation ID with changed
  input conflicts.
- Note and link corrections append an entry revision; prior snapshots remain
  immutable.
- A package may remain visibly unassigned. Reassignment always records the
  exact current Loop and Role Brief revisions.
- Finalization names the exact nonempty ready-source/active-entry set. If other
  sources remain unfinished or rejected, `finalizeSubset: true` produces the
  visible `partial` state instead of hiding them.
- A material proposal pins Loop, Role Brief, material-base, and selected-source
  revisions/digests. Any changed base makes it stale and requires a new review.

## Read, export, and deletion

- Package queries return only owner-authorized display projections. They never
  expose R2 keys, multipart upload IDs, raw owner IDs, or other owners' state.
- Source reads reauthorize D1 ownership, verify locator namespace, size, and
  ETag, support one HTTP byte range, and set private/no-store and `nosniff`
  headers. PDF and generic documents download as attachments.
- Export returns a JSON manifest with display metadata, immutable digests,
  parsed supplied-transcript cues, revisions, and relationship receipts. Exact
  source bytes remain available as individual authorized downloads; they are
  not embedded in the manifest.
- Governed deletion first marks the package deleting, reconciles completed and
  unfinished R2 state, verifies object absence, removes private source and
  entry content, then leaves a package tombstone and material provenance
  receipts. It never deletes or rewrites an already-confirmed Interview
  Material revision.

## Privacy-safe traces

The HTTP module records command, phase, result code, source count, byte count,
and duration. It never logs content, transcripts, filenames, labels, URLs,
filesystem paths, owner/package/source/material IDs, R2 locators, upload IDs,
cookies, or credentials.

## Recovery guarantees

- A failed browser request rereads D1 so open upload sessions remain visible.
- Multipart completion repairs a crash after R2 completion by checking the
  existing object before replaying completion.
- D1 batches use invariant guards so a stale package/source/session cannot
  produce a partial authoritative receipt.
- Cancellation and deletion reconcile R2 before committing the D1 receipt and
  are safe to retry with the exact operation ID.
- There is no automatic transcription, AI analysis, publication, provider
  submission, arbitrary directory scan, or external-link fetch.
